案例研究 —— Verdict

空运合规预检,我自己发起、为货运代理这个领域做的。我把一个早期原型放到一位悉尼货代的 IT 负责人面前,他向我开放了他们真实的单据构成和工作流。单人开发,仍在进行中。

问题

货运操作人员靠手工分检单据:空运提单、发票、装箱单、危险品申报。全部要对着生物安全窗口期、禁止进口条例和空运限制核一遍,而且赶时间。漏掉的代价很贵:货被扣、重新申报、罚款。做这件事的人不需要一个神谕;他们需要一个不知疲倦、并且会把过程摊开给你看的预检器。

塑造了一切的那条约束

一个你没法复现的合规判定是一份责任。所以整套系统建在一条规则上:模型从不做决定。 LLM 负责抽字段、给文档分类、起草跟进邮件。每一个 pass / review / blocked 判定都出自一个确定性规则引擎:在已验证字段之上的纯函数,并以规则集的 SHA-256 快照做版本。任何一个判定,以后都能逐位重放。

做了什么,量了什么

9 种单据类型 · 57 条规则分布在 3 个模块,编码了 ISPM-15、DAFF BMSB 季节性措施、IATA DGR(第 65 版)及一份 ~190 条目的 UN 空运白名单、禁止进口条例、WCO HS 与 Incoterms 2020 · 15 个需鉴权的 REST 端点(JWT、RBAC、IDOR 防护、审计日志) · 中英双语 PDF + OCR 进件 · 表驱动测试套件(~1,000 个用例,含 8 轮对抗测试),由 CI 在测试、类型检查、构建和 lint 四关上卡住 · 抽取在上面那套 511 字段语料上量得 96.3% 严格 / 99.0% 语义。

数据边界与供应商选择

LLM 这一层是手写的 OpenAI 兼容客户端,藏在一个供应商抽象后面。目前指向 DeepSeek,开发期按成本选的:跑完整的 85 份文档评测只要几美分。MiniMax 是自动故障转移。开发期只用合成数据和脱敏数据;prompt 里没有客户的个人信息。因为契约是那层抽象,换成一个满足数据主权要求的供应商 —— Azure OpenAI(悉尼)、AWS Bedrock,或者一个本地模型 —— 是一次配置改动,不是重写。不管换成哪个,确定性内核都把波及面收窄到同一处:无论供应商是谁,它永远只负责起草和抽取。它从不做决定。

诚实的局限

上面是合成数据的 demo;真实系统正在为一个客户开发中,不是一个公开产品。准确率是在那个客户的单据构成里、干净的数字版英文 PDF 上量的。不是扫描件,不是拍照件。规则编码的是我对公开法规的解读,由测试验证,不是由持牌报关行验证。没有任何关于生产流量的主张。
